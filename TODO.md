## P1 — блок «Профиль»

### Что хранить

- [ ] **Подтверждённые факты кандидата:** имя для откликов, контакты по желанию, город/часовой пояс, языки, опыт по местам работы, проекты и достижения. Метрики только из резюме или введённых пользователем фактов.
- [ ] **Резюме:** загрузка PDF/Markdown, список файлов, язык и дата версии, основная версия, просмотр извлечённого текста, удаление и замена с сохранением истории там, где версия использована в отклике.
- [ ] **Навыки:** технологии, опыт и примеры применения; отдельно подтверждённый опыт и «хочу развиваться». Не считать упоминание технологии в вакансии навыком кандидата.
- [ ] **Цели поиска:** направления и их приоритет, желаемые уровни; не смешивать текущую квалификацию с уровнем вакансии, который хочется попробовать.
- [ ] **Условия:** удалённо/гибрид/офис, регионы и страны, часовые пояса, релокация, вид занятости, язык общения, доступность к выходу.
- [ ] **Зарплатные ожидания:** минимум и желаемое значение, валюта, период, до/после налогов, отношение к вакансиям без зарплаты. Не сравнивать суммы разных типов как одинаковые.
- [ ] **Исключения:** компании, отрасли, роли, обязательные ограничения. Для предпочтений отдельно указать «желательно», чтобы не отсекать подходящие вакансии жёстко.
- [ ] **Настройки отклика:** язык, тон, желаемая длина, выбранные контактные данные. Уточнять недостающий контакт перед использованием, а не подставлять выдуманный.

### Как должен работать экран

- [ ] Секции «Обо мне», «Резюме и опыт», «Что ищу», «Условия», «Исключения»; заполнять можно постепенно.
- [ ] Явные состояния: сохранение, сохранено, ошибка, несохранённые изменения. Не терять ввод при смене раздела.
- [ ] Минимум для сбора — выбранные параметры поиска; резюме требуется для персональной оценки/письма, а не для простого просмотра рынка.
- [ ] Предпросмотр: какие запросы и ограничения будут получены из профиля; источник каждого ограничения виден пользователю.
- [ ] Разделить профиль, сохранённый шаблон поиска и параметры одного запуска. Разовое «Backend / Junior» не меняет опыт кандидата и постоянные предпочтения.
- [ ] Версия профиля в оценке и отклике; после изменения показывать, что старые оценки построены на прежней версии.
- [ ] Импорт текущих Markdown-профилей с предпросмотром и подтверждением конфликтов; экспорт для резервной копии.
- [ ] Backend: чтение/обновление профиля, валидация полей, загрузка и извлечение резюме с ограничением размера/типа, результат ошибки парсинга. Секреты провайдеров не возвращать клиенту.

**Критерий готовности:** пользователь сохраняет профиль, перезагружает страницу, запускает поиск и видит те же параметры; персональная оценка ссылается на эту версию и реальные факты из выбранного резюме.

- [ ] Повторные попытки временных ошибок с ограничением, backoff и учётом rate limit; ограниченная параллельность вместо неограниченного увеличения запросов.
- [ ] Видимый результат: получено, новых, обновлённых, исключённых по каждой причине; недоступные источники и достигнутые лимиты.
- [ ] История подборок с параметрами и результатом; повтор запуска с теми же настройками и редактирование копии.

**Критерий готовности:** пустая подборка объясняет причину; изменение фильтров воспроизводимо и не теряет ранее полученные вакансии.

## P2 — БД и перенос данных, вернуться отдельным этапом

Наличие фронтенда не определяет выбор SQLite/PostgreSQL. Для строго локальной программы SQLite упростила бы запуск; PostgreSQL уже описан в Compose и миграции. Рабочее предложение — продолжить с существующим PostgreSQL при принятии зависимости от Docker, не поддерживать обе БД одновременно. Перед этапом явно зафиксировать выбор.

- [ ] Подключить repository к БД; до этого наличие миграции не означает, что данные уже в PostgreSQL.
- [ ] Дополнить схему: версии профиля, резюме/версии, шаблоны поиска, задания и стадии, результаты источников, пользовательские отметки/заметки.
- [ ] Связь многие-ко-многим `search_run_vacancies`: одна вакансия участвует в нескольких подборках. Существующей `fetch_runs` с единственным `source` недостаточно для общего запуска по трём источникам.
- [ ] Разделить внешнюю вакансию `(source, external_id)` и действия пользователя над ней. URL — ссылка, а не единственный стабильный идентификатор.
- [ ] Оценки версионировать по профилю, версии вакансии и модели/промпту; текущий PK `(vacancy_id, user_id)` хранит только одну оценку.
- [ ] Структурировать зарплату/формат и unknown-поля; добавить first_seen/last_seen/updated/closed, не теряя исходный ответ.
- [ ] Определить правила нескольких откликов на одну вакансию, историю черновиков и переходов статуса; не вводить уникальность, которая мешает реальному повторному отклику.
- [ ] Определить локального пользователя без обязательного email для первого запуска. Multi-user предусмотреть в привязках данных, но не строить сервис регистрации заранее.
- [ ] Импорт JSON-выгрузок, Markdown-отчётов, откликов, переписки, профилей и браузерных отметок. Предпросмотр, отчёт ошибок, резервная копия и повторный запуск без дубликатов.
- [ ] Не использовать `ON CONFLICT DO NOTHING` для всего импорта: обновления вакансий и исправления должны переноситься; пользовательские заметки не перезаписывать сырыми данными.
- [ ] Не выбрасывать `seen-vacancies.txt` просто потому, что есть UNIQUE. Уникальность записи не заменяет историю получения и пользовательского разбора; сначала определить, что можно достоверно импортировать.
- [ ] Не извлекать выдуманные числовые score из старых Markdown-отчётов: импортировать только действительно имеющиеся группы/объяснения, остальное оценивать заново при необходимости.
- [ ] Переключение чтения и записи без двух равноправных хранилищ; Markdown/JSON после перехода — экспорт и архив. Старые файлы удалять только после проверки переноса и резервной копии.
- [ ] Проверить применение миграций на пустой БД и обновление существующей. Менять уже применённую `0001` через новые миграции, а не переписывать историю.
- [ ] Резервное копирование и проверяемое восстановление; удаление профиля/данных без случайной потери общих вакансий.

## P2 — организация frontend

- [ ] Разделы: «Вакансии», «Подборки», «Отклики», «Профиль»; технические настройки провайдера — отдельно от фактов кандидата.
- [ ] В списке: сортировка по свежести, зарплате и соответствию; отдельные новые/просмотренные, массовое сохранение/скрытие с возможностью отмены.
- [ ] Сохранять выбранную вакансию, фильтры и позицию списка при обновлении; адресуемые страницы/URL для открытия нужной вакансии и подборки.
- [ ] На мобильном отдельный переход список → карточка → назад с сохранением позиции; управление с клавиатуры и видимый фокус.
- [ ] Показывать загрузку, частичный результат, пустое состояние и ошибки по месту; сообщения об ошибках должны исчезать после успешного исправления.
- [ ] Разделить `app.js` на API-клиент, состояние и экраны/компоненты; оформить CSS по компонентам и токенам вместо длинных строк и накопления переопределений.
- [ ] Определить момент перехода на TypeScript/React: несколько независимых экранов, редакторы и сложное состояние. Не переписывать готовый inbox только ради совпадения со старым roadmap.
- [ ] Проверить ограничения рендера на больших выборках; сначала пагинация, виртуализация только при измеренной необходимости.
- [ ] Отдельно показывать результат фонового поиска и результат кнопки «Обновить подборки», чтобы действия не путались.

## P2 — AI и эксплуатация

- [ ] Ввести интерфейс провайдера оценки/черновиков. Claude CLI временно оставить адаптером; прямой SDK выбирать при необходимости структурированных ответов, контроля стоимости и независимости от установленного CLI.
- [ ] Структурированный результат с валидацией и привязкой к vacancy id; не парсить свободный Markdown как основной API.
- [ ] Версии промптов, модели, профиля и навыков письма; кэширование результата без повторной оплаты неизменённых данных.
- [ ] Оценка длительности/объёма перед большим запуском, лимиты числа вакансий и черновиков, учёт токенов/стоимости при доступности данных от провайдера.
- [ ] Ограничить доступ AI к файлам и инструментам необходимой операцией. Текущий `--dangerously-skip-permissions` — временный локальный механизм, не основа публичного сервиса.
- [ ] Описания вакансий и сообщения рекрутеров считать внешними данными, не инструкциями на выполнение команд; исключить передачу секретов в контекст и логи.
- [ ] Один модуль Go с `cmd/api`, `cmd/fetch` и общими внутренними пакетами, если сохраняется единый жизненный цикл сборки. Не делать микросервисы без самостоятельной нагрузки/эксплуатации.
- [ ] После выделения orchestration в Go оставить `run-search.sh` тонкой обёрткой или убрать. Перенос файла в `scripts/` сам по себе проблему не решает.
- [ ] Привести README, AGENTS, CLAUDE, `.env.example` и команды запуска к одному описанию. Указать фактически автоматизированные источники отдельно от возможностей ручного поиска в чате.
- [ ] Минимальные проверки по рискам: валидация параметров, единственный запуск и отмена, ошибки/частичный результат источников, сохранность данных и импорт. Использовать фикстуры, не реальные платные поиски. Не наращивать тесты ради количества.

## P3 — только после основного сценария

- [ ] Расписание и уведомления: частота, тихие часы, лимиты, отсутствие дублирующих запусков.
- [ ] Аналитика воронки: сколько отобрано, отправлено, ответов и интервью; считать по фактическим статусам, не по количеству сгенерированных файлов.
- [ ] Перед доступом извне: аутентификация, изоляция данных пользователей, защищённые сессии, хранение секретов, лимиты запросов/загрузок/AI. Сейчас оставить localhost.
- [ ] Несколько пользователей и рабочие пространства только после подтверждения такой потребности.
- [ ] Автоматическая отправка откликов — отдельное продуктовое решение с явным подтверждением отправки, не продолжение кнопки генерации.

## Рекомендуемая последовательность

1. Исправить профиль, seen и частичные ошибки; отделить сбор от AI. Результат: надёжный поиск, который не скрывает находки и не генерирует лишние письма.
2. Сделать экран профиля и генерацию одного редактируемого отклика. Результат: законченный личный сценарий в интерфейсе.
3. Добавить устойчивую историю заданий и единое серверное хранение отметок; согласовать этот этап с возвращением к БД, чтобы не строить второй сложный файловый движок.
4. Перенести данные в выбранную БД, добавить серверный каталог и пагинацию. Результат: объём данных и несколько вкладок больше не ломают работу.
5. Развивать оценку, переписку, расписание и аналитику по реальному использованию.

Файловый прототип, Fiber и небольшой JS-фронт сами по себе не были ошибкой: они позволили проверить сценарий. Пересмотра уже требуют смешанные состояния вакансий, разные источники профиля и связка «любой поиск → массовые AI-черновики». БД нужна для целостности и истории; смена фреймворка и перестановка каталогов имеют меньший приоритет.
